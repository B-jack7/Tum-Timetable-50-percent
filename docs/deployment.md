# Deploying the account edition

The working application uses independent application accounts, a Cloudflare-compatible Worker and a persistent D1 database. Users separately bind their own TUMonline and Moodle calendar subscriptions. This is not official university SSO, does not verify TUM identity and never asks for a school password. The retained SAML backend is a future optional integration requiring institutional approval.

## Local HTTPS development

Use Node 24 or newer with the committed lockfile:

    npm ci
    npm test
    npm run check
    npm start

npm start and npm run dev build the UI assets and start server/dev.mjs at https://localhost:8781. The local server generates a temporary self-signed localhost certificate; the browser may require accepting it for the local preview. PORT selects another port. npm run preview reuses assets generated by an earlier build.

Local accounts, hashed sessions, rate buckets and encrypted subscriptions persist in .local/timetable.sqlite. Its matching encryption key is .local/feed-encryption.key. Both are ignored by Git. Keep both across restarts; do not include them in a release or expose the development server as production. The local server applies committed Drizzle migrations before handling requests.

## Worker and D1 production

Run the tests and checks above, then npm run build. The build bundles worker/index.mjs into dist/server/index.js and embeds an explicit UI allowlist. The Worker serves account pages only after session validation. Production requests must reach this Worker rather than a static server serving all of public/.

Deploy through the host's supported Worker/server pipeline. Bind the persistent D1 database under the name DB. The native Sites pipeline collects root drizzle/ for database migrations; retain its generated SQL, journal and snapshots. Apply migrations through deployment before accepting account requests. API handlers never create tables. Other Cloudflare hosts require their equivalent D1 migration configuration.

Supply these values on the server only:

| Setting | Required value |
| --- | --- |
| APP_ORIGIN | Exact public HTTPS origin, without a path or trailing slash |
| FEED_ENCRYPTION_KEY | Securely generated random 32-byte key, encoded as base64 and held in the secret manager |
| DB | Native persistent D1 binding, not a browser-visible database URL |

The runtime must support Node-compatible crypto. Password scrypt uses about 32 MiB working memory and significant CPU time; configure sufficient CPU budget and test real registration/login in production. Do not reduce the KDF parameters to fit an inadequate runtime limit. Confirm the trusted Cloudflare CF-Connecting-IP header reaches the application for address rate limiting. See [the auth contract](auth-local.md) and [Cloudflare crypto documentation](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/).

APP_ORIGIN is configured explicitly because a proxy's internal request address may differ from the public URL. Browser write requests must have this exact Origin. Sessions use Secure/HttpOnly/SameSite=Lax cookies; subscriptions use account/source-bound AES-GCM encryption. Never put secrets into frontend code, build artifacts, logs or Git.

Verify registration, login, logout, expired sessions and two-account isolation at the actual public URL. Anonymous requests must not read account.html, /api/calendar or /api/export.ics. Account/API responses must remain private, no-store. New accounts start empty until their owner binds an official subscription. Login does not grant university API access; calendar activities do not establish assignment submission status.

## Updating a live installation

Deploy new code against the existing DB binding. Preserve FEED_ENCRYPTION_KEY, existing migration history and user records. Generate new Drizzle migrations for deliberate schema changes. Replacing the database removes accounts; changing only the encryption key makes existing subscriptions unreadable. Planned key rotation requires a separate decrypt/re-encrypt migration.

Back up the database and key in separate protected administrative storage, outside Git and release artifacts. Code updates do not require resetting accounts or subscriptions. This version has no self-service password recovery, password-change page, account deletion interface or account administration panel.

## GitHub Pages preview and caching

npm run build:static generates a restricted login-introduction preview. GitHub Pages can serve that preview but cannot run the Worker, bind D1 or provide working account/calendar APIs. The optional manual pages-demo workflow deploys only this restricted artifact; normal CI does not publish. See the [official Pages deployment action](https://github.com/actions/deploy-pages).

No service worker is enabled for this account edition. Personal calendar data, credentials, account pages and API responses must not enter public/offline caches. Do not enable the archived private-edition PWA generator over this application.
